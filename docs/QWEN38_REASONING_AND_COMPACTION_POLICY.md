# Qwen3.8 reasoning and long-context data policy

## Purpose

This document separates three ideas that are easy to confuse:

1. the model can reason while it is serving an agent;
2. a training dataset can teach visible tool-use actions; and
3. a dataset can train the model to emit written reasoning.

They are not the same intervention.  This policy keeps the current
teacher-action dataset scientifically honest and defines the narrow gate for a
future written-reasoning dataset.

It is a data and training-policy document.  It does not authorize a new data
collection, training run, or evaluation.

## What the current SFT corpus contains

The current broad teacher corpus is **visible-action SFT**, not chain-of-thought
distillation.

- It contains successful stronger-teacher trajectories from training task
  families only.
- It trains the model on assistant decisions and `bash` / `submit_report` tool
  calls.  Tool results and copied history have zero loss.
- The dense-corpus builder normalizes an assistant message to role, visible
  content, and tool calls.  It deliberately drops `thinking`, `reasoning`, and
  `reasoning_content` fields before tokenization.
- The native SFT runtime separately rejects a message containing any of those
  three fields.  The regression test in `tests/test_dense.py` proves that a
  private reasoning sentinel cannot enter the action corpus.

This is scientifically valid for the claim it makes: imitation of successful
visible cyber-agent actions under the frozen task/tool contract.  It does **not**
show that the student learned a teacher's private chain of thought, and it must
not be described that way.

The existing broad corpus already clears the project's 20-million-token scale
target: it has 2,886 successful teacher sessions, 496 training task keys,
176,654 supervised assistant responses, and **57,384,881 distinct supervised
target-token occurrences**.  The 32K, 64K, and 96K variants re-group the same
targets into different windows; they are context treatments, not three times as
much independent supervision.

### What this means for the A2 LoRA comparison

The `qwen38-lora-anchor-a2-v1` packet is an action-only comparison against the
paired full-weight treatment.  Both treatments use the same frozen 32K corpus,
base model, task-family exclusions, and task/tool contract.  A2 changes the
adaptation method and its separately qualified learning rate; it does not add
teacher thinking, private reasoning, or extra examples.

This matters when reading a result: any difference between A2 and its paired
full-weight comparator can test the adaptation method under this action-only
dataset.  It cannot establish that either model learned hidden chain of thought
or learned to shorten its own context.  The packet records this explicitly so a
later training or evaluation report cannot silently widen the claim.

## Current context treatment

### Offline SFT

Offline SFT does not perform live context compaction.  It takes a static,
accepted trajectory and creates windows that contain a target action plus a
bounded amount of earlier history.  Earlier copied history is loss-masked; each
accepted assistant target appears exactly once.  There is no truncation of a
target action.

An exported trajectory that uses an opaque `context_compaction` tool is rejected
as a whole.  The export does not provide enough information to reconstruct the
summary or the exact prompt that led to later actions.  Pretending that the
uncompacted history was the prompt would train on a different problem from the
one the teacher solved.

This makes the current action corpus valid, with a stated limitation: a window
can lack early task information that was semantically useful.  The 64K and 96K
arms test whether retaining more real, loss-masked history helps.  They do not
claim to teach the model how to compact a conversation.

### Evaluation

The OpenCode evaluation protocol has a separate live-context contract: Qwen is
served with a 262,144-token context and the harness can automatically compact
and continue a long conversation.  The exact evaluation protocol binds the
harness version, template, tool schema, context reserve, and thinking setting
for both the base and trained model.  The current OpenCode adapter invokes
`opencode run --thinking` and declares reasoning support in its model settings;
those are protocol facts, not training-data permissions.

Evaluation-generated reasoning and summaries are sealed evaluation material.
They must never flow into SFT, RL prompts, reward design, retrieval, or model
selection.  Native compaction during an evaluation therefore does not make
opaque historical teacher compaction usable for SFT.

### RL

The SkyRL episode recorder has a different requirement.  When it creates a
working-memory summary, that summary is generated by the policy itself and is
recorded as its own policy step.  The next action is trained with the exact
changed prompt, sampled token IDs, and log probabilities it actually used.  It
does not flatten the later action behind the old prompt.

That design is necessary for a correct policy-gradient objective.  It is only
an implementation/qualification contract until a run produces a real verifier
reward, a finite optimizer update, a reloadable checkpoint, and release
evidence.  It is not evidence that a completed RL run learned from compaction.

## Thinking mode is an explicit experiment variable

The upstream Qwen3-family documentation describes a thinking-mode switch named
`enable_thinking`, with separate sampling settings for thinking and
non-thinking use.  It also notes that the exact request mechanism depends on
the serving framework.  Qwen3.8 must still bind and test its own pinned
tokenizer template rather than inherit behavior from a nearby Qwen version.
Our serving configurations use a `qwen3` reasoning parser, but that alone does
not prove that every training or evaluation request used the same thinking
behavior.

For any comparison, freeze and record all of the following together:

- model and tokenizer revision plus the exact chat-template bytes;
- the explicit thinking setting and any `preserve_thinking` setting;
- the tool-call parser and tool schema;
- sampling settings, including the total response budget; and
- the served request format used at evaluation.

The relevant upstream reference is the [Qwen thinking-mode
guide](https://qwen.readthedocs.io/en/latest/getting_started/quickstart.html).
It is a template/API reference, not permission to copy a provider's hidden
reasoning into a training set.

## A safe future written-reasoning lane

Do not add a boolean such as `include_thinking=true` to the existing action
corpus.  That would blur two different data contracts.  Instead, create a new,
frozen corpus type only after all gates below pass.

### Allowed sources

The only acceptable written reasoning is reasoning that is both:

1. **authorized for training**, and
2. **visible to the student under the same inference contract**.

The clearest initial source is a fresh Qwen rollout collected with an explicit
student-visible thinking template.  An external teacher is acceptable only when
its contract explicitly says the reasoning is student-visible and trainable.
Generic provider `thinking`, `reasoning`, or `reasoning_content` fields are
private/unknown by default and must be excluded.  Never infer, rewrite,
summarize, or reconstruct hidden thought.

### Required aggregate-only inventory

Before reading any content for corpus construction, run a private inventory
that emits only counts, fixed reason codes, and digests.  It should record:

- source model/harness/template digest and explicit thinking-mode value;
- sessions, task families, and successful eligible sessions by split;
- a fixed visibility class for each source: `student_visible`,
  `private_or_unknown`, or `absent`;
- counts of complete visible reasoning-to-action sequences;
- counts of opaque versus exactly recorded compaction boundaries; and
- a digest of the private source manifest and of the inventory itself.

It must not print or commit prompts, reasoning text, tool output, flags,
credentials, token IDs, or per-session identifiers.  `private_or_unknown` is
an exclusion, not a guess.

### New corpus contract

The new corpus needs a distinct schema and manifest, for example
`cyber_student_visible_reasoning_sft_corpus_v1`, with:

- a source-authorization receipt;
- the exact template and thinking-mode digest used both to generate and train;
- separate accounting for reasoning and action target tokens;
- task-family split proof before any packing/windowing;
- a no-truncation rule for supervised spans; and
- an exact continuation record whenever compaction occurred: pre-summary
  prompt identity, generated summary token identity, post-summary prompt
  identity, and the later action's true prompt identity.

The initial scientific comparison should be a matched action-only versus
student-visible-reasoning treatment with the same task-family split, action
targets, model, template, optimizer, and evaluation protocol.  It answers
whether written, student-visible reasoning helps; it must not be mixed into the
current action-only result after the fact.

### Required tests before any launch

1. A private-reasoning sentinel never appears in serialized training rows or
   supervised token spans.
2. An approved visible-reasoning fixture round-trips through the exact Qwen
   template and has the same token IDs at collection, training, and serving.
3. The corpus builder fails closed for a missing authorization receipt, unknown
   visibility, template drift, or mixed thinking settings.
4. Every task family stays entirely in one split.
5. An opaque compacted trajectory is rejected; an exactly recorded visible
   compaction preserves the real post-summary prompt rather than replaying old
   history.
6. Aggregate inventory output contains only permitted aggregate fields and
   fixed reason codes.

Until these tests and the authorization gate exist, collect more high-quality
visible-action data and run the action-only SFT/RL comparisons.  They are useful
on their own and do not depend on inventing a chain-of-thought dataset.
