Starting-point test · Qwen3.8-27B

Neither old test is a clean baseline.

We tested the same model on 15 public web-security challenges. Qwen Code and OpenCode are two different programs that let the model use tools. Qwen Code produced a useful partial result, but 12 of its 60 attempts had technical problems. OpenCode’s score is unusable because the second AI that checks written security reports never worked.

Fleet training data · 160 tasks reviewed

A broken task tells us nothing about the model.

We examined 160 saved security challenges in which the model could use a website but could not inspect its source code. We kept 89 only after checking that each challenge had run correctly before and that all files needed to run and score it are still available.

160 tasks in the saved list 89 passed both checks Scores were not used for selection
Selection rule

A genuine model failure is useful data. A broken website or broken scoring program is not. We never used model scores to decide which tasks to keep.

01

How 160 tasks became 89

Every task had to pass two checks: a previous attempt completed and scored correctly, and everything needed to run the task again is still present.

Worked correctly before+Can still be run today=89 tasks

The two middle counts are separate, overlapping checks—not a step-by-step funnel. Some tasks passed only one of them; 89 passed both.

02

What “good” means

Every task we kept passed both checks below.

1

It worked in a previous test

An independent record showed that the website started, a model attempt completed, scoring finished with a real number, and the temporary website was removed afterward.

2

We can recreate it

The exact website setup, starting information, hidden answer-checking code, and scoring program are all still available.

03

How we checked the tasks

We chose the checks before looking at whether the model succeeded or failed.

04

Why 71 tasks were excluded

These are missing proof or missing files. They do not mean every excluded task is permanently broken.

A second check found 17 tasks missing their starting information and 11 missing either the hidden answer-checking setup or the exact scoring program. Many of those tasks were already among the 62 without proof of a successful test, so adding these numbers together would count some tasks twice.

How the order was chosen

Early runs answer the biggest questions with the fewest GPUs. Later runs tune smaller details or test whether a promising result repeats.

01

SFT experiment queue

Supervised fine-tuning (SFT) teaches the model to predict the useful actions in saved successful attempts. The first rows compare what examples to learn from before spending many runs tuning smaller numerical settings.

RL experiment queue

Reinforcement learning (RL) lets the model try a task, receive a score from the task’s real checker, and update toward attempts that scored better. The first rows prove the full loop works before larger or more adventurous runs.

03

How to read the order

These are ranked experiment plans, not claims that the listed settings are already best.

1

Compare the source of learning

First compare strong-teacher attempts, Qwen’s own successes, and a mixture while keeping the amount of training and the optimizer settings matched.

2

Find a stable numerical range

Then vary learning rate, batch size, episode group size, and number of passes widely enough to find both under-training and instability.

3

Refine the winning design

Only after a clear winner appears should we tune window extraction, task sampling, reward details, and longer training.

4

Confirm before the final test

Repeat finalists on a second balanced split or random seed. Keep the final Fleet tasks untouched. WebExploitBench may run earlier, but then it counts as development evidence rather than a final independent test.

04

Where the suggested ranges came from

These papers and the working Fleet training code give us sensible starting points. They do not prove that a setting will work on long web-security tasks; every row must earn its place on Fleet’s development tasks.
