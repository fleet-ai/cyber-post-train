02

What the three scores mean

Each percentage counts known security weaknesses, not websites. Higher is better.

Pass@1

Use one designated attempt. Report the percentage of known weaknesses it found.

Pass@3 (Avg.)

Run three attempts separately and average their three success rates. This describes a typical attempt.

Pass@3 (Max)

Count a weakness if any of the three attempts found it. This describes their combined coverage.

Pass@3 (Max) is normally higher because different attempts can find different weaknesses. When more than three attempts were saved, we include every possible group of three rather than choosing the best group.

03

Why the baseline is not a training result

The original model's 11.8% pass rate is valid, but it only tells us how the untrained model performed. To learn whether training helped, a trained checkpoint must face the same task versions with the same tools, limits, randomness settings, and automatic checker. The saved records keep individual task outcomes private, so this public page reports only safe totals.

The correct statement today is: the original-model baseline is complete, but no trained checkpoint has completed its matching side of the comparison. We have not established either an improvement or a decline.

04

What a publishable training result needs next

The original-model side is complete. One selected trained checkpoint must now run on the same 17 development tasks with the same test settings. Only after that side also finishes with valid automatic checking will we compare results. The eight final test tasks remain untouched until a training recipe is chosen.

Only 75 currently meet our strict standard: an earlier attempt proved the exact task ran and scored correctly, the same version is still selected, and the latest review does not mark it as broken.

Selection rule

A genuine model failure is useful data. A broken website or broken scoring program is not. “Production” and “has an automatic answer check” are not enough on their own.

What stays fixed, and what “two epochs” costs

Proposed common setup: exact Qwen3.8-27B; assistant-token prediction loss; AdamW optimizer with β₁=0.9, β₂=0.95, ε=10⁻⁸, no weight decay and gradient clipping at 1. Start the learning rate gradually over the first 10% of updates, then reduce it to zero with a cosine schedule. These optimizer details are our controlled starting choices, not proven optimal values.

Keep the same data, split, training seed (42) and evaluation program within each comparison. W&B records numeric training loss, gradients, learning rate, useful token counts, throughput and checkpoints. We do not add teacher-imitation loss on held-out traces.

An epoch is one pass through the frozen examples. With N examples, effective batch B and E epochs, the kept-final-batch rule gives E × ceil(N/B) optimizer updates. The generator calculates this only when supplied actual example counts. Example count is not task count; two data pools with two epochs can still contain very different amounts of training.

Measure total processed tokens as well as tokens the model learns to predict. Estimate GPU-hours from the exact data length distribution, trainer and node layout, plus export and Fleet dev evaluation. Eight simultaneous nodes is a concurrency limit, not a total compute budget. Do not assume LoRA or a larger batch saves time.

02

Protect the comparison.

The most important decisions are often what the model learns from, what stays hidden, and how success is measured.

Implementation is separate from the proposal.

Then test learning by doing.

Reinforcement learning (RL) learns from fresh attempts scored by the real task checker. This smaller, lower-confidence follow-on plan is not part of the SFT budget selector.

RL settings and prerequisites

Proposed common setup: GRPO (compare rewards within attempts of the same task), full-weight updates, one optimization pass per collection, constant learning rate, clipping range 0.2, token-mean loss, no added KL penalty initially, seed 42. These are hypotheses; preserve the exact qualified Miles implementation rather than silently translating them to another trainer.

Before these full runs, prove real reward variation, a finite parameter update and a reloadable checkpoint. Use the same frozen OpenCode tool program throughout; retain 262,144 live tokens with validated native compaction and separately frozen multi-hour/long-turn budgets. A broken environment or context overflow is not a genuine zero reward. Compacted histories need correct per-segment action probabilities before RL training.

Compare both valid attempt counts and elapsed GPU-hours: 8 tasks × 4 attempts and 4 tasks × 8 attempts each collect 32 attempts, but can take different amounts of time. Do not import scores or any training hints from WebExploitBench.

04

Evidence, not magic numbers.

No source below establishes the optimal settings for Qwen3.8 on Fleet. The closest evidence is security-task SFT on Qwen3; same-size agent recipes and controlled optimization studies supply useful alternatives.

05

How we decide what comes next.

Use the same held-out Fleet development tasks for screening. Repeat promising recipes with new training seeds; retain an untouched final Fleet set. WebExploitBench is a report-only transfer check: freeze each checkpoint and test setup before evaluation, and never use those results to choose later recipes.

Do not run every row automatically. If the first three recipes all fail to improve task success, inspect training-signal coverage and data quality before spending on adapters or dozens of optimizer settings.
